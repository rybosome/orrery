# Scene authoring

Orrery loads one scene per navigation. A scene declares its SPICE kernels, coordinates, renderable bodies, primary light, playback coverage, and viewer defaults. The viewer reads the same definition for geometry, rendering, camera presets, and share restoration.

The production catalog currently contains Sol. Use its package as the reference:

- [Sol definition](../src/scenes/sol.ts)
- [Sol bodies and appearance](../src/scenes/solBodies.ts)
- [Scene contract and validator](../src/scenes/sceneDefinition.ts)

## Add a scene

1. Create a TypeScript definition under `src/scenes/` and check it with `satisfies SceneDefinition`. Give the scene a stable URL slug such as `my-system`.
2. Put the scene’s approved kernels and maps under `public/static/`. Define the ordered pack with `kernels.custom(...).pick(...)`. Use distinct virtual kernel paths and keep intended load precedence. The viewer resolves relative asset URLs against Vite’s deployment base.
3. Choose a common SPICE frame and observer. For each body, declare a stable viewer `id`, its actual SPICE `body` target, radius in kilometers, and optional body-fixed frame. Preserve any physical NAIF ID used for inspector metadata separately from the ephemeris target. Sol, for example, queries Jupiter’s barycenter (5) and labels it with Jupiter’s physical metadata (599).
4. Choose a continuous UTC coverage interval for the entire pack and an initial epoch in ET seconds. The viewer converts the endpoints using the scene’s LSK. Check actual position and frame queries at both endpoints and several interior times. SPK segment bounds are in ET, so a UTC timestamp with the same calendar fields can fall outside the segment.
5. Set the primary light, startup camera focus, scale presets, and any per-body home poses. Add guide specifications to bodies that need them. Each guide declares a SPICE center, span, and refresh interval. A center can be absent from the rendered roster. Supply a period only when the path describes a periodic orbit.
6. Register the definition in `sceneCatalog.ts` after the checks below pass. Keep the scene and body IDs stable so existing v2 links can continue to resolve.

## Appearance and alignment

Set each body’s surface color and optional textures, roughness, and atmosphere. Maps use a right-handed body-local frame with north at +Z. A positive `textureLongitudeOffsetRad` rotates the surface texture geometry around body-local +Z before the SPICE body-frame orientation is applied. Frame axes continue to show the SPICE orientation. Cloud maps inherit the same fixed alignment by default, and a drift rate of zero keeps authored cloud landmarks fixed.

Use one primary light body per scene. Stellar surface color, emission, and bloom are declared on that body’s appearance. The point light follows its ephemeris position, while optional terminator effects receive the direction from each body to the star. The viewer uses constant visual light intensity.

## Validate and release

- Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, and `pnpm e2e`.
- Extend the real-kernel coverage test to exercise the declared body targets and fixed frames. Check guide placement and coverage edges, including any center without a visible body. At a fixed epoch, switch camera focus and check that the planet’s lit hemisphere stays fixed.
- Verify direct navigation to the registered route, a v2 link generated by that scene, and both released Sol v1 URL shapes. Verify that the scene ID in the v2 payload matches the URL. Check that deep links fetch the JavaScript bundle, kernel and WASM bytes, and textures.
- The Pages deployment workflow checks routes and asset responses after deployment. For a preview protected by Cloudflare Access, it verifies the same build with Wrangler’s Pages runtime. Production smoke checks run against the public site after the deployment from `main`.

Sol v1 aliases and defaults are part of the released wire format. Keep them in the snapshot reader when changing scene data. V2 links store a scene ID and scene-local focus ID. They use the currently deployed version of that scene’s assets and kernels.

During the Sol rollout, the release with the v2 readers is the rollback point for the homepage and writer cutover. If the cutover needs to be reverted, deploy a build that can still open the v2 links users have already shared.
